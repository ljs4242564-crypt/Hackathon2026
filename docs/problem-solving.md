## 1. 검색 첫 결과가 현재 학기 정답이 아닐 수 있음

- 문제: 게시판 검색 결과 순서만 따르면 과거 학기나 다른 프로그램 공지를 선택할 수 있다.
- 재현 방법: `tests/searchService.test.ts`, `scoreCandidate`의 연도·학기·제외어 조건 확인.
- 초기 가설: 키워드 포함 여부만으로 충분할 수 있다.
- 시도한 접근: 제목/부서 키워드, 연도, 학기, 게시일을 점수화했다.
- 실패한 접근: 검색 결과의 첫 항목을 그대로 답으로 쓰는 방식은 근거가 약하다.
- 확인한 원인: 게시판 검색 순서와 질문의 적용 학기·의도는 동일하지 않다.
- 선택한 해결책: 현재 연도 +12, 학기 +3, 핵심 키워드 +6, OCU·학점교류·대학원 등 비대상 공지 -12 규칙을 적용한다.
- 검증 방법과 결과: `tests/searchService.test.ts`의 후보 점수화 테스트 통과.
- 남은 한계: 제목에 연도·학기가 없거나 표현이 바뀌면 점수 조정이 필요하다.

## 3. SSRF와 외부 redirect 위험

- 문제: 외부 HTML의 링크 또는 사용자 질문의 URL을 그대로 요청하면 내부망·비공식 호스트 접근 위험이 있다.
- 재현 방법: `tests/domainValidator.test.ts`, `tests/searchService.test.ts` 실행.
- 초기 가설: `scnu.ac.kr` 문자열 포함 확인으로 충분할 수 있다.
- 시도한 접근: URL 파싱 후 HTTPS, 정확한 hostname, 허용 path, 포트, 인증정보, IP literal을 검사했다.
- 실패한 접근: suffix/substring 검사는 `scnu.ac.kr.attacker.example`을 막지 못할 수 있다.
- 확인한 원인: 최초 URL뿐 아니라 redirect 목적지도 신뢰 경계를 넘을 수 있다.
- 선택한 해결책: `redirect: manual`, 최대 2회, 매 단계 Allowlist 재검증을 적용한다.
- 검증 방법과 결과: 허용 redirect 성공, 공격자 호스트 redirect·localhost·IP·비표준 포트 차단 테스트 통과.

## 4. 기본 테스트가 실제 외부 사이트에 의존함

- 문제: `tests/chatRoute.test.ts`의 도서관 질문이 기본 `fetch`를 사용해 네트워크 상태에 따라 지연·실패할 수 있다.
- 재현 방법: 테스트에서 `chatRoute.request` 호출 후 검색/원문 Fetch 의존성 경로 확인.
- 초기 가설: 공식 사이트가 안정적이므로 단위 테스트에서도 호출 가능하다.
- 시도한 접근: 개별 서비스에는 이미 fetcher 주입을 일부 사용했다.
- 실패한 접근: timeout만 늘리면 테스트 속도와 재현성이 계속 외부 상태에 좌우된다.
- 확인한 원인: 라우트가 구체 서비스 함수를 직접 호출해 테스트에서 전체 의존성을 교체하기 어렵다.
- 선택한 해결책: 작은 resolver 팩토리/의존성 주입으로 기본 테스트는 fixture만 사용하고 실제 사이트는 `test:live`로 분리한다.
- 검증 방법과 결과: 라우트 resolver를 fixture로 주입했고 기본 테스트 54개가 외부 인터넷 없이 통과했다. 실제 사이트 확인은 `npm run test:live`로 분리해 1개가 통과했다.
- 남은 한계: live 테스트는 공식 사이트 상태에 따라 실패할 수 있으며 배포 차단 조건으로 쓰지 않는다.

## 5. 공개 URL이 HTTP 200이어도 장애 본문일 수 있음

- 문제: 과거 점검에서 `Site Unavailable` 본문이 보고되어 상태 코드만으로 서비스 성공을 판단할 수 없다.
- 재현 방법: `curl -L -D -`로 헤더와 본문, `/api/health` Content-Type을 함께 확인한다.
- 초기 가설: HTTP 200이면 정상이다.
- 시도한 접근: 루트 HTML 식별자와 Health JSON을 함께 검사했다.
- 실패한 접근: 상태 코드만 검사하면 플랫폼 오류 페이지를 정상으로 오판한다.
- 확인한 원인: 과거 장애의 플랫폼 내부 원인은 현재 저장소 기록만으로 확인할 수 없어 `추가 확인 필요`다.
- 선택한 해결책: 본문·Content-Type·실제 UI를 배포 판정 조건에 포함한다.
- 검증 방법과 결과: 2026-09-26 20:03 KST에는 실제 앱 HTML과 `status: ok` JSON을 확인했다.
- 남은 한계: 간헐 장애 탐지를 위한 지속 모니터링은 아직 없다.

## 6. Worker와 브라우저에서 공식 게시판 요청이 다르게 동작한 문제

- 실패한 접근: 확인 가능한 기록 없음.

## 7. 넓은 snapshot 키워드가 같은 카테고리의 다른 질문에 오답을 반환함

- 문제: 공식 사이트 조회 실패 시 질문과 주제가 다른 snapshot이 답으로 선택되었다.
- 재현 질문 또는 명령: `도서관에서 책 빌리는 방법 알려줘`, `도서관 위치 알려줘`, `교내장학금 신청 방법 알려줘`, `근로장학금 모집 기간 알려줘`를 upstream 실패 조건에서 실행한다. 교정 전 공개 배포에서도 2026-09-26 22:38 KST에 동일 문제가 재현되었다.
- 원인: `snapshotRepository.ts`가 카테고리 일치 후 `matchedKeywords`와 snapshot 키워드를 양방향 부분 문자열로 비교하고, 점수가 0보다 크면 가장 높은 항목을 반환했다.
- 실패한 설계: 카테고리가 같고 `도서관` 또는 `장학금` 같은 넓은 단어 하나만 겹쳐도 해당 카테고리의 대표 snapshot을 안전한 fallback으로 간주했다. 이 방식은 “답이 없음”보다 관련 없는 답을 선택했다.
- 선택한 수정: snapshot마다 허용 `intent`, `requiredAll`, `requiredAny`, `excluded` 규칙을 선언했다. 분석된 용어를 정확히 비교하고, 모든 조건을 충족한 항목만 반환하며 일치 항목이 없으면 `null`로 처리한다.
- 자동 테스트: `tests/answerResolver.test.ts`에 대표 질문 5개 fallback과 오매칭 방지 질문 8개를 함께 실행한다. `npm test`에서 교정 후 기본 테스트 71개가 통과했다.
- 수정 전후 결과: 수정 전에는 도서관 위치 질문이 운영시간 snapshot을, 교내장학금 질문이 국가장학금 snapshot을 받았다. 수정 후 upstream 실패 시 모두 `upstream_unavailable`, `answerMode: unavailable`, `cacheHit: false`, 빈 출처를 반환한다.
- 남은 한계: 엄격한 규칙 사전에 없는 동의어와 심한 오타는 올바른 snapshot이 있어도 사용하지 못할 수 있다. 오답 방지를 위해 이 경우에는 추측 대신 unavailable을 선택한다.

## 8. 공식 사이트 fallback과 호스팅 플랫폼 전체 장애는 다른 장애 계층임

- 문제: 앱 내부 fallback은 국립순천대학교 upstream의 timeout·HTTP·파싱 실패를 처리하지만, Genspark 호스팅 자체가 `Site Unavailable`을 반환하면 앱 코드와 `/api/health`, `/api/chat`이 실행되지 않는다.
- 재현 질문 또는 명령: `curl -L -D - <배포 URL>/`, `curl -L -D - <배포 URL>/api/health`, `curl -X POST -H 'Content-Type: application/json' --data '{"question":"이번 학기 중간고사 언제야?"}' <배포 URL>/api/chat`으로 status, Content-Type, body marker를 함께 검사한다.
- 원인: 학교 공식 사이트 장애는 애플리케이션 내부 신뢰성 경계 안에 있지만, 관리형 호스팅의 라우팅·Worker 가용성 문제는 앱이 실행되기 전의 외부 계층이다. 2026-09-26 밤의 플랫폼 장애에 대한 내부 원인은 현재 저장소 자료만으로는 확인할 수 없어 `추가 확인 필요`다.
- 실패한 설계: HTTP 200만 확인해 플랫폼 오류 HTML을 정상 앱으로 판정했고, 내부 snapshot fallback이 있으면 공개 서비스도 항상 열릴 것으로 가정했다.
- 선택한 수정: 배포 smoke test에 앱 title marker, `Site Unavailable` 부재, Health JSON과 `status: ok`, Chat JSON을 포함한다. Health에 배포 버전 식별자를 추가한 뒤 기대 commit과 비교하고, 관리형 배포가 계속 실패하면 다른 Cloudflare 배포 경로나 정적 백업/데모 영상을 준비한다.
- 자동 테스트: 로컬 테스트는 upstream 장애에서 snapshot/unavailable 전환을 검증한다. 호스팅 계층은 배포 후 curl 기반 smoke test로 별도 검증하며, 하나라도 실패하면 배포 완료로 판정하지 않는다.
- 수정 전후 결과: 이전 점검에서는 루트와 Health가 HTTP 200 HTML `Site Unavailable`, Chat이 405였다. 2026-09-26 22:38 KST에는 기존 URL이 복구되었지만 오매칭이 계속 재현되었다. 2026-09-26 23:02 KST 새 관리형 배포에서는 앱 HTML, Health JSON, Chat JSON과 `releaseId: 2026-09-26-corrective-1`을 확인했고, 도서관 대출·위치 질문은 관련 없는 snapshot 없이 `upstream_unavailable`을 반환했다.
- 남은 한계: 같은 Genspark 플랫폼의 이전 URL은 독립 장애 격리가 되지 않는다. 현재 독립 백업 URL과 1분 데모 영상은 준비되지 않았으며 제출 전 별도로 마련해야 한다.


## 2026-09-27 최종 검토: 범위 오매칭과 상태 교정

앞부분은 과거 실행 기록이다. 현재 결과는 SUBMISSION_STATUS.md를 우선한다.

새 finalScope.test.ts 초기 15개 중 8개 실패를 재현했다. S1~S4는 평일/주말, 제외 표현, 1차/2차, 복수 장학금 문제이고 L1~L3는 HTTP 200에서도 학기·절차·요일이 다른 근거를 반환하는 문제다. 실제 학교가 오답을 보냈다는 주장이 아니라 독립 fixture 검증이다.

공통 topicPolicy에 범위 계약을 추가하고 snapshot에 차수 메타데이터와 주말 필수 조건을 적용했다. live 문장별 필터와 최종 formatter 검증으로 답변·필드·출처를 통제한다. 장학금 기간은 적용 학년도와 학기가 있어야 하며 게시일만으로 확정하지 않는다. 1~2월 일정 적용 학년도도 이전 연도로 맞췄다.

기존 성공 HTTP 제외 자료 테스트 4개의 기대값은 upstream_unavailable에서 정확한 not_found로 변경했다. 단언을 삭제하거나 허용 상태 목록을 넓히지 않았으며 upstreamStatus=ok와 빈 sources를 추가 검증했다. Worker 정상 장학금 fixture에는 적용 학기 근거를 추가하고 성공 단언은 유지했다. 기본 127개와 새 19개, 총 146개 통과.

대체 타입 검사에서 새 tuple 추론 오류 1개를 실제 수정 후 통과했다. 기본 타입 실행기 panic, live timeout, Wrangler preview 오류는 실패 그대로 기록한다. React/Hono 구조와 보안 경계는 유지했다. 도서관 홈 빠른 질문은 주말로 수정하고 PM2 cwd를 __dirname으로 이식 가능하게 했다.
